# Runtime and compiler contracts

**Proposal only.** This file preserves low-level invariants from the companion CORE design. Layouts and limits are candidates, not an approved ABI. Verify them against the actual Rust implementation and supported targets before freezing any representation.

## Value and address representation

The proposal uses an eight-byte, eight-byte-aligned tagged value with no destructor or implicit retain/release behavior. Ordinary numbers retain IEEE-754 semantics, including negative zero. Numeric NaNs are canonicalized before tagging so a NaN bit pattern cannot be mistaken for a reference. Internal empty, hole, and uninitialized sentinels never escape through guest-visible returns, property reads, host conversion, debugger values, or exceptions.

The proposed tag allocation is:

| Tag | Candidate meaning |
|---|---|
| Non-NaN IEEE-754 bits | Number |
| `0x7ff8` | Canonical numeric NaN |
| `0x7ff9` | Signed 32-bit integer payload |
| `0x7ffa` | Boolean |
| `0x7ffb` | Null, undefined, and private sentinels |
| `0x7ffc` | Object reference |
| `0x7ffd` | String reference |
| `0x7ffe` | Symbol reference |
| `0x7fff` | BigInt reference |

This encoding is viable only if every tagged heap reference fits a verified address envelope. Establish the reservation and growth contract before guest allocation begins. If a target cannot provide it, use a portable split tag/payload representation selected before isolate creation. Never truncate a pointer or switch layouts after guest execution starts. Do not assume that all arm64 or x86-64 hosts share the same address layout.

Compiler values distinguish tagged JS values, integer and floating-point scalars, relocatable GC references, native pointers with provenance, and Wasm linear-memory offsets. A linear offset is not a native pointer. Wasm floating-point operations retain typed semantics and do not round-trip through JS number tagging unless a JS boundary requires it.

## Object layout and property access

The source design proposed a 16-byte GC header and a 48-byte ordinary-object header on its selected 64-bit ABI. Treat these as a candidate layout. Verify size, alignment, and field offsets during compilation and artifact installation. The header is private runtime storage, not an embedding API.

Shapes are immutable descriptions of object category, prototype, ordered descriptors, key-to-slot mapping, slot counts, and layout flags. Descriptor attributes are part of shape identity. Shape IDs are isolate-local and cannot be reused while objects, feedback, code, observers, or frames may still refer to them. Shape metadata may be pinned while its guest references remain traced and relocatable.

An ordinary own-property fast path checks receiver kind and expected shape, loads the authoritative inline or external slot, then checks the loaded value's representation if the next operation requires it. A shape proves the property's slot and descriptor kind; it does not prove the loaded value's type. Stores preserve descriptor checks and GC barriers. Adding or redefining properties, setters, proxies, exotic objects, dictionary objects, and unsupported cases take a complete semantic path.

Prototype-dependent reads guard the receiver and every dependency needed to justify the result. Absence is a dependency too. Arrays distinguish packed values, holes, dictionary storage, and `undefined`; a hole may require prototype lookup. Typed arrays use separate buffer state for detach and resize. A pointer or bound derived before an unknown call is invalid unless a guard proves it remains valid.

Do not expose long-lived Rust references into guest object storage that generated code can mutate or a moving collector can relocate. Host access uses rooted handles, isolate-owned operations, or a scoped no-GC/no-reentry lease whose type carries the exclusion capability.

## Bytecode, interpreter, and feedback

Bytecode is an immutable function artifact containing instruction storage, constants, register and argument layout, operation sites, handlers, loop entries, and source positions. The encoding is a proposal; preserve instruction-boundary, branch, operand, handler, and loop-state contracts even if its word format changes. Verify generated bytecode in debug/stress modes and always verify serialized bytecode before use.

Generic bytecode owns full language semantics. Operations that can call user code, coerce values, throw, allocate, suspend, or perform host effects must describe those effects explicitly. Specialized compiler operations cannot substitute for a missing generic interpreter path.

The interpreter uses an explicit VM frame and iterative dispatch loop rather than recursively re-entering a Rust interpreter for each guest call. A frame retains function and realm, PC, registers, callee/receiver/arguments, environment, completion and exception state, handlers, continuation, and resource-limit state. Suspension captures traced frame state.

Runtime observations live outside immutable bytecode and are allocated lazily. Feedback may record shapes, representations, call targets, or useful loop execution, but it is bounded and weakly held where it must not retain arbitrary guest objects. A megamorphic site remains semantically executable. Feedback only proposes a guarded specialization; it does not establish proof by itself.

## IR legality and facts

The design separates language-specific ScriptIR/WasmIR from a shared typed CoreIR and MachineIR. Each function carries a signature, typed blocks, explicit normal/exception/trap edges, memory regions, safepoint and reconstruction records, and source/logical-frame provenance. Memory regions distinguish guest heap, Wasm memory, native stack, native allocations, runtime metadata, and shared atomic memory.

Facts carry their source and lifetime. The proposed classes are:

| Fact | Allowed use |
|---|---|
| Proven | A semantic change may rely on it within its valid region. |
| Guarded | A semantic change may rely on it while the guard and dependencies remain valid. |
| Observed | May guide profitability or propose a guard; does not prove an invariant. |
| Declared | May guide checking or propose a guard; does not establish runtime shape, immutability, or representation. |

Unknown host calls invalidate unprotected heap and buffer facts. Safepoints invalidate raw derived heap addresses. TypeScript `number`, `readonly`, casts, `any`, declaration files, or a stable-looking property do not independently prove integer width, own-slot layout, immutability, or safety from getters/proxies. A guard validates runtime values before entering specialized code; guard failure returns to generic semantics rather than inventing a new type error.

For example, a numeric annotation can propose a number guard, but a call with a string must still follow JavaScript behavior unless a separate native contract rejects it at the boundary. An object property annotation does not prove an own slot or exclude a getter. A type assertion is not runtime evidence.

Effects initially remain conservatively ordered. A pass may split effect ordering only after proving memory regions independent. Arithmetic modes, overflow, NaN/signed-zero behavior, conversions, pointer provenance, atomics, exception ordering, and observable effects remain explicit. Rust undefined-behavior or aliasing assumptions cannot be imported into JavaScript or Wasm merely because they share a backend.

## Deoptimization, OSR, and calls

Compiled activations retain interpreter-compatible frame homes. GC references have writable mapped homes at safepoints. Numeric intermediates may stay unboxed between safepoints and use boxing/materialization recipes on exit. Inlined frames retain enough logical state to reconstruct their interpreter frames.

A resume record identifies the logical frame chain, bytecode PC, realm/environment/callee/receiver/arguments, registers, handler/finally state, pending completion, resource limits, and materialization recipes. Before-effect exits resume at the operation; after-effect exits preserve the completed result and resume after it; abrupt exits preserve the exception. A getter, callback, imported function, host effect, or completed allocation must never run twice because a later guard failed.

OSR imports an interpreter frame transactionally. All representation and dependency checks happen before the compiled activation becomes visible. Failure leaves the original interpreter frame intact. Retired code stays alive while any active frame or return continuation can still use it.

The engine ABI is private and explicit. Calls describe callee, receiver, argument count and values, realm/environment, and constructor state. Wrappers are classified as pure leaf, allocating, reentrant host, or throwing; each class has distinct safepoint, root, invalidation, and completion obligations. Rust unwinding must not cross generated guest frames. Guest exceptions, Wasm traps, deoptimization, native failures, and policy denials use distinct completion paths.

## WebAssembly and the shared backend

Decode and validate an entire module before instantiation or execution. Individual function validation/compilation may proceed after shared module declarations and types are known. Keep Wasm stack validation, traps, memories, tables, and instance identity explicit. Unsupported declared features fail validation; they are not silently approximated.

Begin memory access with overflow-safe bounds checks. Memory growth or imported calls invalidate derived backing pointers unless the relevant proof still holds. Shared memory uses explicit atomic semantics. Linear-memory bytes never enter the JS tracing graph. Managed Wasm references use explicit layout descriptors and barriers while remaining distinct from ordinary JS property objects.

The shared backend owns typed IR verification, machine constraints, register allocation, emission, relocations, and separate GC, resume, debug, and unwind metadata. Validate fixed/tied registers, call clobbers, spills, roots, branches, and literal references before publication. A GC map cannot replace a logical frame resume map, and neither can establish native unwind correctness.

JIT publication writes only into private unpublished memory during the platform's approved write window, completes relocations and cache synchronization, restores protection on every exit path, installs metadata, then publishes the entry with release ordering. Avoid writable-and-executable code as a convenience. AOT uses symbolic relocations and checks target/runtime/schema compatibility before load.

Optimization passes declare which IR dialects and semantic modes they accept. The initial fast tier is limited to local CFG cleanup, liveness, type/range propagation with provenance, exact-mode constant folding, local forwarding, dominated-guard elimination, representation selection, bounded inlining, and dead-code removal. Loop motion, unrolling, scalar replacement, and vectorization are later optional work. They require proof that callbacks, exceptions, traps, allocation, safepoints, and reconstruction state preserve their order; numeric-looking operands alone do not make a guest loop safe to reorder.

## TypeScript and Rust boundaries

TypeScript checking and TypeScript execution are distinct. A checked build waits for module-level diagnostics, but ordinary execution need not wait for whole-program checking. Parser or checker resource exhaustion is inconclusive, not success. Type facts retain provenance beside executable terms. Runtime-bearing TypeScript syntax lowers into engine-owned IR; annotations do not generate hidden runtime checks or layouts.

An AOT package may contain native functions, generic fallback bytecode, module initialization descriptions, literals, symbolic runtime bindings, and root/reconstruction metadata. It contains no process addresses or live isolate shape IDs. Loading binds symbolic items to the current realm and runtime after compatibility checks. Dynamic import, `eval`, and `Function` retain their documented behavior when included; an AOT mode that excludes them must declare and check a different input contract.

The Rust frontend retains MIR until an explicit semantic adapter lowers the supported subset. Native functions use a documented ABI-safe adapter; the spelling of an `extern "C"` boundary does not permit a C implementation dependency. Rust `Result`, panic, ownership, and aliasing behavior are converted explicitly. Panics never unwind across generated guest frames; any catch occurs in a Rust wrapper before returning to the engine.

Raw movable guest references are not ordinary Rust FFI values. Rust calls use rooted handles, scoped capabilities, or explicitly verified GC-aware operations. Cross-language inlining starts only for leaf numeric functions whose arithmetic modes and ownership rules agree; general Rust borrowing or alias guarantees cannot be inferred from a JavaScript function signature.

The proposal lists explicit WebAssembly support groups rather than an undifferentiated “Wasm supported” claim: core numeric/control operations, multi-value and bulk memory, reference types and indirect calls, SIMD, shared memories and atomics, memory64 and multiple memories, managed references, and exception handling. The owner must select the release contract. Unsupported declared features fail validation clearly.

## Licensing and source reuse

The source designs considered several open-source parser, Wasm, allocator, scheduler, and compiler components. They do not grant blanket approval to copy or link any implementation. Before reuse, record the exact component, version/revision, license, required notices, feature closure, native/build dependencies, and maintenance owner. For restricted-license sources, port behavior from specifications and independently written designs; do not copy source code. Recheck every current license and dependency edge before implementation or publication.
